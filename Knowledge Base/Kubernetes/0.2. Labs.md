# Kubernetes Hands-On Labs & Proof of Work

To truly master the **Kubestronaut** curriculum and pass practical command-line exams (CKA, CKAD, CKS), passive reading must be backed by deployments and break/fix debugging. 

Every lab below is framed as a **functional deployment** with explicit self-verification commands. Always execute verification steps before marking a topic completed.

---

## ⚡ Lab 0: Offline Study & Manifest Workflows (All Certifications)
### Lab 0.1: Fast Offline YAML Manifest Discovery & Cluster Application
- **Objective:** Master instant terminal discovery and cluster application of canonical Kubernetes YAML manifests without relying on an internet connection or browser tab searching during timed CNCF practical exams.
- **Prerequisite Tools:** Ensure your sparse documentation repository is initialized via [setup_k8s_offline_docs.sh](file:///Users/mk/Documents/01_Active_Work/GitHub/Cloud-Engineering-Vault/Knowledge%20Base/Kubernetes/scripts/setup_k8s_offline_docs.sh) and the Golang tool [kdoc.go](file:///Users/mk/Documents/01_Active_Work/GitHub/Cloud-Engineering-Vault/Knowledge%20Base/Kubernetes/scripts/kdoc.go) is built/aliased.
- **Execution Checklist:**
  - [ ] **Step 1:** Search for canonical examples of a zero-trust `NetworkPolicy` offline using the Golang systems tool:
    ```zsh
    kdoc yaml netpol
    ```
  - [ ] **Step 2:** Inspect and extract an authoritative Nginx Deployment or Service manifest directly into a working file:
    ```zsh
    kdoc yaml nginx-deployment --dump > /tmp/exam-deployment.yaml
    ```
  - [ ] **Step 3:** Apply the extracted manifest to your local Kind cluster and verify immediate reconciliation:
    ```zsh
    kubectl apply -f /tmp/exam-deployment.yaml
    kubectl get deployments -o wide
    ```
  - [ ] **Step 4:** Clean up the test workload:
    ```zsh
    kubectl delete -f /tmp/exam-deployment.yaml && rm -f /tmp/exam-deployment.yaml
    ```
- **Verification Command:** `kdoc list NetworkPolicy` (should return all canonical NetworkPolicy example files from `~/.local/share/k8s-offline-docs/content/en/examples`).

## 🏗️ Lab 1: Foundational & Cluster Operations (KCNA / CKA)
*Reference Notes: [[1. KCNA - Cloud Native Associate]] | [[2. CKA - Kubernetes Administrator]]*

### Lab 1.1: Local HA Cluster Provisioning via Kubeadm & Kind
- [ ] Deploy a multi-node Kubernetes cluster (1 control plane, 2 worker nodes) locally using `kind` or EC2 instances with `kubeadm`.
- [ ] Install a Container Networking Interface (CNI) plugin (Weave Net, Calico, or Cilium).
- [ ] **Verification Command:**
  ```bash
  kubectl get nodes -o wide
  kubectl get pods -n kube-system --field-selector=status.phase!=Running
  ```

### Lab 1.2: etcd Backup and Disaster Recovery Restore
- [ ] Take a consistent live snapshot of the `etcd` database using trusted TLS PKI certificates.
- [ ] Simulate cluster data loss by deleting critical Deployments in the default namespace.
- [ ] Restore the cluster state from the backup file by amending the static Pod manifest `/etc/kubernetes/manifests/etcd.yaml`.
- [ ] **Verification Command:**
  ```bash
  ETCDCTL_API=3 etcdctl --endpoints=https://127.0.0.1:2379 --cacert=/etc/kubernetes/pki/etcd/ca.crt --cert=/etc/kubernetes/pki/etcd/server.crt --key=/etc/kubernetes/pki/etcd/server.key endpoint health
  kubectl get pods --all-namespaces
  ```

### Lab 1.3: Gateway API Traffic Routing & Ingress
- [ ] Install CRDs for Kubernetes Gateway API in your cluster.
- [ ] Configure a `Gateway` resource listening on port 80 and an `HTTPRoute` splitting traffic 80/20 between two app versions (Canary release).
- [ ] **Verification Command:**
  ```bash
  kubectl get gateway,httproute -A
  curl -H "Host: myapp.local" http://<gateway-ip>/
  ```

## 💻 Phase 2: Workload Architecture & Application Lifecycle (CKAD)
*Reference Notes: [[3. CKAD - Application Developer]]*

### Lab 2.1: Multi-Container Pod Design Patterns
- [ ] Deploy a simple web server Pod utilizing a **Sidecar container** that continuously polls a Git endpoint or processes logs into `/var/log/app.log` via an EmptyDir volume.
- [ ] Configure an **Init Container** that blocks main container execution until a dependent database service port (e.g., MySQL 3306) responds.
- [ ] **Verification Command:**
  ```bash
  kubectl get pods my-app -o jsonpath='{.status.initContainerStatuses[*].ready}'
  kubectl logs my-app -c sidecar-container
  ```

### Lab 2.2: Kustomize Overlay Deployments (Dev vs Prod)
- [ ] Create a base Kustomize layout for a stateless Golang microservice with Deployment, Service, and ConfigMap.
- [ ] Implement `overlays/dev` and `overlays/prod` directories using transformers to alter replica counts, CPU limits, and environment prefixes without altering base YAML.
- [ ] **Verification Command:**
  ```bash
  kustomize build overlays/prod | kubectl apply --dry-run=client -f -
  ```

## 🔒 Phase 3: Advanced Security & Runtime Threat Enforcement (CKS / KCSA)
*Reference Notes: [[4. KCSA - Security Associate]] | [[5. CKS - Security Specialist]]*

### Lab 3.1: CIS Benchmarking & API Server Hardening
- [ ] Run an auditing Job using Aqua Security's `kube-bench` against your control plane node.
- [ ] Fix identified critical warnings: configure anonymous authentication to `false`, enable explicit audit log rules, and set secure TLS cipher suites in `/etc/kubernetes/manifests/kube-apiserver.yaml`.
- [ ] **Verification Command:**
  ```bash
  kubectl logs job/kube-bench | grep -E "(FAIL|WARN)"
  ```

### Lab 3.2: Zero-Trust Network Policies & RBAC Confinement
- [ ] Create a dedicated service namespace (`tenant-a`) with a default-deny ingress and egress `NetworkPolicy`.
- [ ] Create a specialized ServiceAccount (`app-reader`) bound to a Role granting only `get` and `list` permissions on ConfigMaps in `tenant-a`.
- [ ] **Verification Command:**
  ```bash
  kubectl auth can-i delete pods --as=system:serviceaccount:tenant-a:app-reader -n tenant-a # MUST return no
  kubectl describe netpol -n tenant-a
  ```

### Lab 3.3: Runtime Threat Detection with Falco & Image Vulnerability Scanning
- [ ] Scan an application container image for severe CVEs and exposed secrets using `trivy image`.
- [ ] Deploy Falco daemonset monitoring eBPF/syscall events. Trigger a critical security alert by spawning an interactive terminal execution (`kubectl exec -it <pod> -- /bin/bash`) inside a running production container.
- [ ] **Verification Command:**
  ```bash
  trivy image --severity HIGH,CRITICAL nginx:1.18.0
  kubectl logs -l app=falco -n falco | grep "Notice A shell was spawned in a container"
  ```
